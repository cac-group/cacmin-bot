## 2026-10-03 — Fix rate-limit muting and error logging

**Problem.** Production showed 257 `Failed to apply rate-limit mute
{"userId":1194167473,"error":{}}` and zero `Rate-limit mute applied`.
Rate-limit violations deleted the message and posted a warning, but never
restricted the user in Telegram.

**Root cause.** `messageFilter` passed `ctx.telegram` (a `Telegram` client) to
`RateLimitService.muteUser`, which dereferenced `bot.telegram`. A `Telegram`
client has no `.telegram` property, so every call threw a `TypeError` at the
first `getChatMember` and was swallowed by the surrounding `catch`. Introduced
with the feature in `a2c719d` (v2.19.0); muting had never worked — only message
deletion did.

**Changes.**

- `muteUser` now takes a `Telegram` client and applies the explicit
  `CHAT_MUTE_PERMISSIONS` deny set instead of deriving an empty object from the
  member's (usually absent) permissions.
- The mute date is clamped to at least now + 31s; Telegram treats an
  `until_date` under 30 seconds away as a permanent restriction.
- Permission snapshots merge over `CHAT_RESTORE_PERMISSIONS` on restore (a
  partial snapshot would otherwise silently deny omitted permissions), and are
  refreshed on re-mute.
- `releaseMuteIfAllowed` no longer lifts Telegram restrictions that belong to an
  active jail, matching `cleanExpiredMutes`.
- `logger` serializes `Error` values inside metadata instead of collapsing them
  to `{}`, so future failures are diagnosable.
- Sticker logging uses `config.botIdentity.stickerPackName` rather than a
  hardcoded `CACGifs` comparison.
- Regression tests cover the API call, the stored mute row, the clamp, the
  expiry restore, and the jail-safety skip.

**Also in this release.** The centralized-constants work in `src/config.ts`
(see `logs/2026-10-02.md`) had been left uncommitted; it ships here too.

**Verification.** `bun run lint`, `bun run build`, and `bun run test` (196
passing) all green.

## 2026-10-03 — Centralize chat muting across every mute path

**Problem.** The earlier fix only made rate-limit muting work. Every other mute
path (jail, flood limiter, reaction spam, identity block, duel, restriction
violations) called `restrictChatMember` directly, and each captured permissions
inconsistently or not at all. Restores were split between `cleanExpiredJails`
(which unconditionally applied `CHAT_RESTORE_PERMISSIONS`) and the rate-limit
cleanup, so a mute often deleted messages without restricting the member, and a
jail expiry could hand back more permissions than the member had.

**Changes.**

- New `src/services/chatMuteService.ts` owns Telegram muting: `muteMember`
  (deny-all, clamp, capture binding, announce) and `restoreMember` (restore the
  captured binding, refuse to restore an administrator status, announce).
  `user_rate_limit_mutes` now records the deadline and binding for every mute
  kind, keyed on `user_id`.
- All mute call sites route through it: `JailService.applyTelegramMute` for
  jail/flood/reaction/identity/duel/restriction, `chatMuteService.muteMember`
  for the duel "muted" consequence, and `RateLimitService.muteUser` for
  rate limits.
- `cleanExpiredJails` and `cleanExpiredMutes` restore from the stored binding;
  a missing binding leaves Telegram's own `until_date` to lift the restriction.
- Short `@user has been muted.` / `@user has been unmuted.` chat notices, skipped
  when no username is known.
- `config.intervals.rateLimitMuteCleanupMs` renamed to `muteCleanupMs`
  (`MUTE_CLEANUP_INTERVAL_MS`), since it now clears every mute kind.

**Verification.** `bun run lint`, `bun run build`, and `bun run test` (197
passing) green.

## 2026-10-03 — Key chat mutes by kind, close over-grant on manual release

**Problem (review findings).** The first centralization stored every mute kind
in one `user_id`-keyed row, so a short jail and a long rate-limit mute
overwrote each other, and `cleanExpiredMutes` deleted the binding while a jail
was still active, leaving nothing for `cleanExpiredJails` to restore. `/unjail`
and bail payment also still applied `CHAT_RESTORE_PERMISSIONS` directly,
over-granting and racing the cleanup timers.

**Changes.**

- `user_rate_limit_mutes` now has a `kind` column and composite primary key
  `(user_id, kind)` (migration 012, rebuild with foreign keys off). Existing
  rows become `rate_limit`.
- `chatMuteService`: `muteMember(member, kind, until)` keeps the furthest-out
  deadline per kind; `releaseMute(member, kind)` is per-kind and idempotent, only
  re-granting chat permissions when no kind remains active; `releaseMember` is
  the single manual release used by `/unjail` and bail payment and refuses to
  re-apply permissions to an administrator.
- Mute kinds are threaded through every call site (`jail`, `reaction_spam`,
  `identity_block`, `flood`, `duel`, `restriction`, `rate_limit`).
- `cleanExpiredJails` releases the `jail` binding, falling back to standard
  member rights only for legacy jails with no stored binding.

Additional fixes from the third review pass:

- The active-mute check in `messageFilter` now reads `MAX(muted_until)` across
  kinds, so an expired row for one kind cannot mask an active mute of another.
- `releaseMute` deletes first and uses the DELETE's affected-row count to
  arbitrate, so overlapping cleanup runs restore and announce at most once.
- `RateLimitService.clearLimits`/`clearUsage` delete only the `rate_limit` kind,
  leaving jail/flood/etc. bindings intact.
- `releaseMember` restores the permissions captured at release time when no
  binding was stored, instead of unconditionally granting standard rights.

**Tests.** Migration 012 rebuild/idempotency coverage, per-kind row survival,
shorter-mute-never-shortens-a-longer-one, stale-rate-limit-row-does-not-clear a
live jail, and a new `chatMuteService` suite (restore, idempotent release,
administrator binding, no-binding fallback, mixed-kind release).

**Verification.** `bun run lint`, `bun run build`, and `bun run test` (206
passing) green; migration 012 dry-run against a copy of the production DB
succeeds with zero rows affected and no FK violations.
