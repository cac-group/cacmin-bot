## 2026-09-12 — Tighten reaction spam and add flood limiter

**Problem.** Reaction spam enforcement was kicking/banning too aggressively: the
only exemptions were owners/admins and accounts older than 14 days, so the
`elevated` role and long-time lurkers with few messages were still caught. There
was also no coarse flood limiter for message bursts.

**Changes.**

- `users.message_count` column added (created in `initDb`, `ALTER TABLE` for
  existing DBs). `messageFilter.ts` increments it for every group message from a
  non-whitelisted, non-owner/admin user.
- `reactionSpam.ts` now exempts any user with `message_count >= 5` ("new" user
  threshold, `NEW_USER_MESSAGE_LIMIT`) and any elevated role via
  `checkIsElevated`. Account-age logic removed.
- New `src/services/spamLimiterService.ts`: synchronous in-memory sliding window
  returning the burst to delete. `messageFilter.ts` uses it to delete the last 5
  messages and jail the sender for 5 minutes (Telegram restrict + DB jail), with
  no chat message. Thresholds adjustable via `SPAM_LIMIT_*` env vars.

**Tests.** Added `tests/unit/spamLimiter.test.ts` (limit, burst, window expiry,
per-user/chat isolation, disable flag, pruning). Suite: 158 passing; build,
lint clean.

**Follow-up.** `bot.ts:118,122` still updates a non-existent `users.elevated`
column (dead SQL); left untouched. `reaction-spam.md` is new.

## 2026-09-13 — Backfill message_count from the message index

**Problem.** After the reaction-spam change deployed, established members were
still kicked (`AUTO_KICK reason=reaction_velocity`): `users.message_count` was
introduced at deploy time, so 2184 of 2216 users sat at 0 and were classified
as "new" until they each sent five more messages.

**Fix.** Migration 005 backfills `users.message_count` from the explorer
message DB (`INDEXER_DB_PATH`), grouping strictly by the author's user id
(`messages.author_user_id`, falling back to `user_id`) — never by display name.
Counts only raise the existing value. `user_id` alone only covers ~3% of
messages; `author_user_id` is the identity-resolved column and covers ~98%.
If the indexer DB is absent the migration grandfathers existing users instead.

**Residual.** Users with no indexed group messages (including long-time
lurkers) stay at 0 and remain reaction-check eligible. Measured coverage on
production: 298 bot users had ≥5 indexed messages, 398 had 1–4, 1520 had none.

## 2026-09-13 — No permanent bans + reaction "new user" age fallback

**Policy.** The bot must never permanently ban: enforcement is temporary jails
and kicks only.

- Reaction profile match (`reactionSpam.ts`) changed from `banChatMember` to a
  kick. Velocity was already a kick.
- Identity block (`identityBlocks.ts`) changed from permanent ban to a
  temporary jail: `jailIfBlockedIdentity` mints `users.muted_until` +
  `jail_events` via `JailService` and restricts chat for
  `IDENTITY_BLOCK_JAIL_MINUTES` (default 1440 = 24h). Message-source matches
  still delete the triggering message.
- Updated help text in `identityBlocks.ts`, `spamReacts.ts`, `helpTree.ts`.

**Option B.** Reaction "new user" gate now exempts a user who has
`message_count >= 5` **or** a tracked account ≥14 days old
(`NEW_USER_MAX_AGE_SECONDS`). The age fallback only applies when `created_at`
is known, so never-recorded users stay new.

**Why.** ~1,520 bot users have zero indexed group messages (lurkers / DM-only),
so a pure message-count gate kept classifying established members as new and
subjecting them to reaction kicks.

**Tests.** Updated `tests/unit/identityBlocks.test.ts` (jail assertions, jail
and user services mocked). Suite: 158 passing; build and lint clean.

## 2026-09-14 — Username placeholders + active identity crawl

**Placeholder fix.** No-username users were stored as `"unknown"` (729 rows),
which collided and polluted alias lookups. Now stored as `user_<id>`;
`isPlaceholderUsername` excludes `unknown`/`user_<id>` from alias recording and
resolution.

**Active crawl.** Added `IdentityCrawlService` + `/crawlidentities [count|reset]`
(owner only) and a 5-minute background batch (200 users). It walks
`telegram_users.user_id` with a missing username, calls `getChatMember` for the
configured group, records the profile into the explorer identity tables
(`recordProfile`, source `telegram-crawl`) and updates existing bot usernames.
Cursor/done live in `system_state`; pass completion idles until reset. Throttled
at 60 ms; users who left count as unavailable.

**Tests/docs.** Added placeholder + update-existing tests; suites 168 (bot) pass,
lint/build clean. Docs: `dev-docs/user-identity.md`.

## 2026-09-14 — Crawl 429 handling

`IdentityCrawlService` now detects a 429 (Telegraf `error.code === 429`,
`error.parameters.retry_after`), sleeps `retry_after + 250ms`, and retries the
same user up to 3 times. If it persists, the batch pauses and the cursor stays
at the last fully resolved id so the user is not skipped. Non-429 errors are
still treated as unavailable (left/deleted) and advance the cursor. Added
`tests/unit/identityCrawl.test.ts` (retry, persistent-limit pause, definitive
skip). Suite 171 passing; lint/build clean.

## 2026-09-27 — Auto-apply member tag on join (MEMBER_TAGS)

**Request.** A member (@Niels277, resolved to Telegram user id 1194167473 from
the production bot DB) leaves and rejoins often; his "Neil" member tag had to be
re-added by hand each time.

**Capability.** Telegram Bot API `setChatMemberTag` sets a custom member tag.
Bot must be an admin with `can_manage_tags` (verified: production bot
`Judge_CACC` in `-1001540576068` has it), groups/supergroups only, 0-16 chars,
no emoji.

**Change.** `config.memberTags` parses env `MEMBER_TAGS` (`<user_id>:<tag>`
pairs) into a `Map<number, string>`, keyed by numeric id (usernames are mutable).
`handlers/membership.ts` calls `applyMemberTag` on both join paths
(`new_chat_members` and the `chat_member` join transition). telegraf 4.16 has no
`setChatMemberTag` typing, so it goes through the untyped `callApi`; failures
log a warning and are swallowed so join tracking still runs.

**Stats persistence.** Confirmed unchanged: no code deletes/resets a user row on
leave; `users`, `user_memberships` and every per-user table are id-keyed.
@Niels277's row (2418 messages) and membership record persist across rejoin.

**Config.** Set `MEMBER_TAGS=1194167473:Neil` in `/etc/cacmin-bot/cacmin-bot.env`
and restart the service. Code ships via the normal GitHub release / auto-update.

**Tests.** `parseMemberTags` cases in `tests/unit/config.test.ts`; join-tag
cases in `tests/unit/membership.test.ts` (applies for known user, skips unknown,
skips missing chat, swallows API failure).
