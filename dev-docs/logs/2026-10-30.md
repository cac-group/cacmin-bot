# 2026-10-30 — Multi-token ledger and CAC on Osmosis

**Scope.** Added a second supported token, CAC (`factory/osmo1q77…/cac`, six
decimals) on Osmosis, without disturbing the existing JUNO economy. The bot now
has one ledger keyed by `(user_id, denom)` instead of one balance per user.

**Transport decision.** Osmosis is gRPC-only and uses exactly one endpoint:
Polkachu `osmosis-grpc.polkachu.com:12590` (plaintext). There is no LCD, REST,
or Tendermint RPC fallback. `src/services/osmosisGrpcService.ts` owns the
channel and uses the generated `cosmjs-types` bank/auth/tx clients for balances,
`GetTx`, `GetTxsEvent`, signing, and `BroadcastTx`.

**Data model.** Migration 018 rebuilds `user_balances` with a composite
`(user_id, denom)` primary key, adds `denom` to `transactions`, and adds
`denom`/`network` to `processed_deposits`. Existing balances become `ujuno`.
Deposit watermarks are stored per network (`juno` / `osmosis`) because their
heights are unrelated.

**Behaviour.**
- `LedgerService` methods take an optional `denom` (default `ujuno`), so every
  gamble, fine, bail, giveaway, and treasury path keeps working unchanged.
- The deposit listener polls JUNO over RPC and CAC over gRPC `GetTxsEvent`.
- CAC withdrawals are signed locally (`MsgSend`, `SIGN_MODE_DIRECT`) and
  broadcast with `BROADCAST_MODE_SYNC`; the bot pays uosmo gas from the derived
  `osmo` address. CAC has no internal network fee.
- `/balance` shows both tokens; `/deposit`, `/verifydeposit`, `/claimdeposit`,
  `/processdeposit`, `/withdraw`, and `/send` accept an optional
  `juno|cac` token and default to JUNO.

**Verification.** `bun run build`, `bun run lint`, and `bun run test`
(281 passing) green. The gRPC client was exercised against the live Polkachu
endpoint for `Balance`, `GetTx`, and `GetTxsEvent`. Migration 018 was
applied to the local `data/bot.db` and preserves existing JUNO balances.

**Doc-Impact.** README, LEDGER, `.env.example`, `dev-docs/architecture.md`, and
wallet/deposit help text updated. No deployment performed.
